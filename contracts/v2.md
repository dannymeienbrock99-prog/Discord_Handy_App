# Modstempel 2 – verbindlicher interner Vertrag

Version 2.0.0 / Android versionCode 8. Keine Webhooks mehr. Deployment separat als eigener HTTPS-Node-Server; keine Discord-Geheimnisse in der APK. Die Serveradresse ist in der App einstellbar. Es werden ohne echte Konfiguration keine Anmeldung oder Erfolge simuliert.

## Backend

Node, HTTP-Server hinter HTTPS-Reverse-Proxy. Private atomare persistente Datenbankdatei, Single-Process-Betrieb. Discord OAuth Authorization Code mit HTTPS-Callback `/oauth/callback`, `identify guilds guilds.members.read`; Access-/Refresh-Token nur verschlüsselt im Backend. Bot-Token und Client-Secret nur Server-Umgebung. Kategorien: `modstempel`, `stream`, `big_match`, `general`, `poll`. Für Beiträge keine frei übergebenen Discord-Payloads akzeptieren.

Antworten immer JSON `{ok:true,...}` oder `{ok:false,kind,message,retryAfterMs?}`. Fehlertexte bereinigen, keine Rohantworten/Secrets. Kind `auth`, `forbidden`, `validation`, `network`, `rate_limited`, `unconfigured`, `uncertain`, `permanent`. Kein automatisches Retry eines unklaren Discord-POST.

### Auth

- `GET /health` → `{ok:true,app:"Modstempel",apiVersion:2,configured:boolean,message?}`.
- `POST /v2/auth/start {challenge}`: Der private native Verifier besteht aus 32 Zufallsbytes, dargestellt als Base64url ohne Padding (43 Zeichen). challenge ist SHA256 über die UTF-8-Zeichenfolge dieses Verifiers, dargestellt als 64 kleine Hex-Zeichen. → `{ok:true,loginId,authorizePath,displayCode,expiresAt,intervalMs:3000}`. authorizePath ist ausschließlich ein relativer same-origin Pfad `/oauth/start/<loginId>`. TTL zehn Minuten. displayCode besteht aus Buchstaben/Ziffern und einem Bindestrich, ohne Unterstrich.
- Browser `GET /oauth/start/<loginId>` leitet zu Discord; zufälliger OAuth-state, HTTPS-Callback. Callback speichert nach korrektem State die bestätigte Kontoidentität; Anzeige Konto + Gerätecode im Browser.
- `POST /v2/auth/poll {loginId,verifier}` → `{ok:true,status:"pending",intervalMs:3000}` oder `{ok:true,status:"authorized",sessionToken,user,expiresAt}`. Falscher Verifier gewährt nichts. Einmalige Claim-Bestätigung: derselbe gültige Claim darf für maximal zwei Minuten dieselbe Session zurückgeben (Netz-/Speicherfehler dürfen Anmeldung wiederholen, keine neue Session erzeugen). Native speichert Token vor UI-Erfolg.
- `POST /v2/auth/cancel {loginId,verifier}`.
- Authenticated `GET /v2/session` → `{ok:true,user,expiresAt}`; `POST /v2/auth/logout` widerruft die App-Session.
- `user={id,username,displayName,avatarUrl?}`. Nur geprüfte Kontoidentität verwenden.

### Ziele und Rechte (Bearer-App-Session)

- `GET /v2/guilds` → `{ok:true,guilds:[{id,name,iconUrl?,canConfigure,botReady}],user}`. Schnittmenge beziehungsweise erkennbare fehlende Bot-Installation anzeigen.
- `GET /v2/guilds/:guildId/setup` → `{ok:true,guild:{id,name},botReady,canConfigure,moderatorRoleId,roles:[{id,name,color,mentionable}],channels:[{id,name,type,capabilities:{modstempel,stream,big_match,general,poll},reason?}],canCreateEvents,installUrl?}`. Text- und Ankündigungskanäle 0/5. Rechte für Benutzer UND Bot, inklusive Channel-Overwrites/Timeout, serverseitig berechnen. capabilities berücksichtigen Embed+Send+View+Erwähnung; Upload/Poll bei Mutation extra prüfen.
- `PUT /v2/guilds/:guildId/moderator-role {roleId}` nur echter Serververwalter; Rolle aus diesem Server, !=guildId. → aktualisiertes Setup.
- `GET /v2/guilds/:guildId/install` → `{ok:true,url}`. Nur Discord-Bot-Installations-URL der eigenen App, kein automatisches Installieren.
- `GET /v2/guilds/:guildId/events` → `{ok:true,events:[{id,name,description,startsAt,endsAt,location,url,status}]}`.

## Aufträge

`POST /v2/operations`: JSON `{operation}` ohne Bild, Multipart mit Feldern `operation` (JSON des Auftrags) und `image` (Originalbytes) mit Bild. Native sendet keine beliebigen URLs/Headers. Max Bild 8 MiB, JPG/PNG/WebP; Metadaten/Hash mit Datei abgleichen.

`operation={id,type,actorId,guildId,channelId?,moderatorRoleId?,category?,createdAt,sendBefore?,data,image?}`.

- id: zufällige UUID oder 16–80 Zeichen `[A-Za-z0-9_-]`; an Session-Nutzer gebunden. `actorId` muss aktuelle Discord-User-ID sein.
- type `post`: category wie oben. data `{title,text,startsAt?,poll?}`. Titel1–120, Text0–1800; Poll `{question,answers:[string],durationHours}` mit 2–10 Antworten, 1–55 Zeichen, Frage1–300, Dauer1–168. `stream` bekommt die bekannten drei Antworten, `poll` eigene Antworten. `modstempel`, `big_match`, `general` ohne Poll. image ist bewährte `{ref,name,mime,size,width,height}`-Metadatenstruktur.
- type `stamp`: category `modstempel`; data `{action,at,sessionId,name,team,note,activeMs,pauseMs,totalMs,startedAt}`. Nur Moderatorrolle oder Verwalter, Benutzeridentität aus Session, nicht aus freiem Anzeigenamen. Kein Bild/Poll.
- type `scheduled_event`: data `{title,description,startsAt,endsAt,location}`; ausschließlich EXTERNAL, Ort1–100, Titel1–100, Beschreibung0–1000; Start Zukunft, Ende danach. Kein zusätzlicher Kanalpost/Ping, weil Nutzer dies für Events nicht ausdrücklich verlangt hat.

Ziel und Kategorie werden bei Annahme gespeichert; Role-ID muss zur damals bestätigten Moderator-Konfiguration passen. Später alle Rechte erneut prüfen, aber gespeichertes Ziel niemals umleiten. Modstempel erwähnt genau die ausgewählte Rolle. Andere Beiträge erwähnen `@everyone`. allowed_mentions verhindert zusätzliche User-/Rollen-Pings aus freiem Text. Bei Bild+Poll pingt nur die erste Nachricht; Poll-Nachricht kein zweiter Ping. Kein Bild+Poll in derselben Discord-Nachricht.

Status `GET /v2/operations/:id` → `{ok:true,operation:result}`. Expliziter Retry `POST /v2/operations/:id/retry {acknowledgeUncertain:boolean}`. Derselbe Auftrag/ID, bestätigte Teile nicht wiederholen. Vor Discord-POST Phase atomar als `sending` speichern. Nach Prozessrestart `sending` als `uncertain`; nicht blind erneut senden. Eigene dauerhafte Idempotenz plus Discord nonce/enforce_nonce für Nachrichten. Bei unklarem Event keine automatische Neu-Erstellung.

`result={id,type,status,stage,error?,retryAfterMs?,imageMessageId?,imageChannelId?,messageId?,channelId?,eventId?,url?,imageUrl?,poll?}`. Status `pending`,`sending`,`sent`,`failed`,`uncertain`,`skipped`; stage `image`,`message`,`poll`,`event`. Bei Bild+Poll Bild-ACK vor Poll dauerhaft speichern. Nur bestätigter letzter Schritt ergibt `sent`. GET eines pending-Auftrags darf ihn NICHT senden; Wiederaufnahme durch POST mit derselben ID oder expliziten Retry. Bekannte 429/Offline-Fehler können mit derselben ID erneut angenommen werden. Fehlgeschlagene Aufträge benötigen Retry, nicht erneutes initiales POST.

`GET /v2/operations/:id/poll` → `{ok:true,poll}` für bestätigte Umfrage im ursprünglichen Kanal. Ergebnisse optional, unbekannte Zähler nicht als0 ausgeben.

## Native Bridge (asynchrone actions)

- `backend_status`, `configure_backend {url}`, `auth_begin`, `auth_poll`, `auth_cancel`, `auth_logout`.
- `guilds`, `guild_setup {guildId}`, `moderator_role {guildId,roleId}`, `bot_install {guildId}` (validierten Browser öffnen), `scheduled_events {guildId}`.
- `operation_send {operation,imageRef?}`, `operation_status {operationId}`, `operation_retry {operationId,acknowledgeUncertain}`, `poll_results {operationId}`.
- `open_discord`: vorhandene Kanal-/Nachrichten-IDs plus erlaubtes `{guildId,eventId}` für Event-URL.

backend_status → `{ok:true,configured,origin,serverReady,authenticated,user?,expiresAt?,pendingLogin?:{expiresAt,displayCode,intervalMs},message?}`. configured bezeichnet den lokal gespeicherten Origin; serverReady true/false/null den konfigurierten/noch unkonfigurierten/unbekannten Serverstatus. SessionToken/Verifier niemals an JS zurückgeben. Session/Verifier nativ AES-GCM speichern. Native konfigurierter Origin nur HTTPS, keine Credentials/Queries/Fragmente/Variablenpfade. Originalbild-Multipart an festen Backend-Endpunkt, 200-Sekunden-Watchdog; GET/kleine API45Sekunden.

## Core / Migration

Neue Web-Core-Datei `core-v2.js`, nutzt reine Zeit-/Bildfunktionen aus bisherigem `ModstempelCore`; aktive App wird Modstempel V2. Speicherung bleibt in derselben nativen Datei, version2 mit profile/sessions/events plus `legacyArchive`, `selection`. `posts` und `eventOperations` sind abgeleitete Snapshot-Listen aus events und keine zusätzlichen Speichertabellen. Vor v2-Schreiben archiviert Native originalen v1-Zustand. Alte offene Dienste lokal fortsetzbar/beendbar ohne alten Webhook; alte Aufträge als Archiv markieren und niemals automatisch an Bot umleiten. Keine stillen Daten-/Bildlöschungen.

Root liefert UI-Core-API gesondert; serverseitiger Auftrag ist alleinige Quelle für echte Discord-Zustellung. Native alter send/check/read_poll/storeWebhook deaktiviert. Settings zeigt echte fehlende Backend-/Discord-Konfiguration, keine erfundenen verbundenen Server.
